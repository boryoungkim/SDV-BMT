# SDV-BMT v1.0 — release notes

**SDV-BMT v1.0 — twelve reference models on the GPU and on three NPUs.** Five YOLOX detectors (COCO), three
DeepLabV3+ segmenters (Cityscapes), CenterPoint-Pillars (nuScenes LiDAR) and three Llama models (MMLU and synthetic
speed inputs) run with their datasets on an NVIDIA GPU, the reference accelerator. NPU ports run the YOLOX detectors
on a Mobilint MLA400, DeepLabV3+ R-18 on a BOS Eagle-N and the Llama models on a FuriosaAI RNGD card. One command
runs a model end to end and writes its metric table.

Release date: 2026-11-19. Tag `v1.0`, package version 1.0.0. License: Apache-2.0 ([`LICENSE`](../../LICENSE)).

> SDV-BMT is a research benchmark framework. Its Model-level measurements do not establish WCET, FTTI,
> ISO/PAS 8800 compliance, ISO 26262 compliance, SOTIF compliance, or vehicle-level safety. Percentile latency is
> distribution characterization, not a worst-case timing guarantee. `max_observed` is not WCET. GPU results are
> reference-accelerator results, not NPU results. Results of different devices are shown side by side and are not a
> ranking.

## What is new since v0.1.2

- **3D detection: CenterPoint-Pillars** (mmdetection3d nuScenes checkpoint) on the 162 mini samples of the four
  official-val scenes and on all 6,019 val samples, with **Model-level Metric Set v1.2** (v1.1 plus eight nuScenes
  detection metrics; selectable, the default stays v1.1).
- **Run series**: one dataset selection runs as consecutive ordinary runs (parts) and is evaluated as one result.
- **LLM path** (`python -m sdv_bmt.llm`): Llama 3.2 1B / 3B Instruct and Llama 3.1 8B Instruct on the GPU with vLLM
  and on a FuriosaAI RNGD card with furiosa-llm; TTFT, TPOT, end-to-end latency and MMLU accuracy, with its own
  bundle format and catalog (`sdv-bmt-llm-v1`).
- **Mobilint MLA400 port** of the five YOLOX detectors: int8 compiled models on one ARIES chip in single-core mode,
  through the native measurement plane.
- **BOS Eagle-N port** of DeepLabV3+ R-18: a BF16 plan on a TTNN executor built against the BOS SDK in a pinned
  container. The DUT config pins the executor and its source; a benchmark run needs a qualification receipt written
  from complete L1 evidence on the NPU. The Eagle-N baseline replays its own rate, chosen with the GPU family rule.
- **Metric table and one-command runs**: `python -m sdv_bmt.cli.table` and `python -m sdv_bmt.llm table` write one
  metric table per model ([`docs/metric_table.md`](../metric_table.md)); `tools/run_model.sh <model>` validates, runs,
  evaluates and writes the table, on the GPU or on the NPU named by the model's suffix (`-mla400`, `-eagle-n`,
  `-rngd`); `tools/show_metrics.py` prints a table in a readable form.

## Fixed

- The measure watchdog of the native adapters with `asap` replay killed any `asap` window after a fixed time
  whatever its item count. It now allows one request timeout per planned item.

## What 1.x keeps

Within 1.x these do not change; a change that breaks them is 2.0:

- the commands `sdv-bmt validate`, `run` and `evaluate` and their exit codes (0 success, 1 run failed, 2 rejected);
- the experiment, input, workload and DUT configuration formats (`schema_version: 1`; fields are only added);
- the evidence bundle format (manifest, events, outputs, quality reference, `series.json`): bundles written by 1.0
  are read by every 1.x `evaluate`;
- the names and definitions of the metrics of Metric Set v1, v1.1 and v1.2 (new metrics go into new catalog
  versions only);
- the metric table columns and row kinds.

**Experimental** (may change within 1.x): the NPU adapters (`mobilint_aries`, `bos_eagle_n`) and their DUT options,
which follow the vendor SDKs; the LLM path; the tools under `tools/`, including `tools/run_model.sh`.

## Compatibility

- v0.1.x evidence bundles and evaluations are read as before; the default catalog is still Metric Set v1.1.
- Python ≥ 3.10; runtime dependency PyYAML only. Native: g++ (C++17) and make; the NVIDIA runner needs CUDA 13.0
  and cuDNN 9; the MLA400 runner needs the Mobilint qbruntime; the Eagle-N executor and runner are built in the BOS
  container with the BOS SDK. The LLM path needs its own measurement environments (vLLM, furiosa-llm;
  [`docs/llm_benchmark.md`](../llm_benchmark.md)).
- No model files, compiled models, datasets or images are included. COCO, Cityscapes, nuScenes, MMLU and the Llama
  models are used under their own terms; see [`THIRD_PARTY_NOTICES.md`](../../THIRD_PARTY_NOTICES.md).

## Not included

- Driving scenarios, hardware stress and the Scenario × Stress matrix.
- The measurement extensions for result attribution that the v0.1.2 notes planned for "v0.2"; they move to 1.1.
- DeepLabV3+ R-50 and R-101 on the Eagle-N (they run on the GPU).
- System-level (Autoware) evaluation, WCET / FTTI and functional-safety claims, and the other items listed as not
  included in v0.1.0.

## Known limitations

- One reference GPU and one card of each NPU; batch 1, N = 1, one replay rate per model family on the GPU.
- The Eagle-N baseline of DeepLabV3+ R-18 replays a lower rate than the GPU family rate, so its timeliness results
  are not at the same rate as the other devices'.
- The reference hosts are shared; host load is logged only between runs, and host preemption is not observed.
