# GPU reference results — SDV-BMT v0.1.2

> Research benchmark results on a **reference accelerator** (an NVIDIA GPU), not NPU results and not a GPU
> ranking. Percentiles characterize the measured distribution; `max_observed` is the largest observed value in
> that population, not WCET. Deadlines are evaluation parameters, not FTTI. Nothing here establishes ISO/PAS 8800,
> ISO 26262 or SOTIF compliance or vehicle-level safety.

This page summarizes the evidence behind the v0.1.2 model extension: five YOLOX detectors on COCO and three
DeepLabV3+ segmenters on Cityscapes. The raw evidence bundles are not part of the repository (they contain
host-local details), and no COCO or Cityscapes image or annotation is redistributed. Every number below was taken
from the bundles and their bundle-only evaluations.

Models are shown side by side. A difference between two models is **not attributed** to model size or to any
other factor: the models differ in more than one condition, and the contrast guards treat a pair with different
workloads as invalid.

## Setup

| item | value |
|---|---|
| accelerator | NVIDIA RTX PRO 6000 Blackwell Max-Q Workstation Edition, one GPU (GPU 0), `execution_kind = actual`, role `reference_accelerator_validation` |
| software | NVIDIA driver 580.119.02 (CUDA driver API 13.0), NVRTC 13.0, cuDNN 9.1.0 (pip `nvidia-cudnn-cu12` 9.1.0.70); FP32, batch 1; cuDNN math type default (whether TF32 was used is not observed) |
| host | the v0.1.0 reference host: a **shared multi-user host** (other users' CPU load present); the native runner pinned to the CPUs of the GPU's NUMA node; host state logged right before every timed run |
| admission | N = 1, queue 0, `drop_new`, request timeout 1 s, 32 untimed precondition requests; deadline = frame period |
| GPU guard | a run was started only when no compute process was on GPU 0 (this held for every run below) |
| method | per model: offline conversion to a cuDNN plan → algorithm table obtained with the heuristic policy and pinned → numeric check against ONNX Runtime (CPU) → golden capture (asap) → five fixed-rate baseline runs, model order rotated each round |
| ranges | "a–b" is the minimum and maximum over the five baseline runs of a model; a description, not a statistical test |

### 2.2 Replay rate

The rate rule fixed before the measurements: the highest of 30, 20, 15, 10, 5, 2 and 1 Hz whose frame period
`floor(1e9 / rate)` is at least 1.25 × the largest DUT-service of the three golden captures. The largest was
184.14 ms (R-101), so all three models run at **2 Hz** (deadline 500 ms).

### 2.5 Operating record

- The GPU reported power-cap throttling during every DeepLab run (the GPU's own power limit, unchanged); the
  timings hold under that limit.
- One R-101 run started with a host load average of 148.8 (1 min) from other users, all harness CPUs above 90 %
  busy. By the rule fixed beforehand, CPU load is recorded and the run proceeds. Its values are inside, or at the
  edge of, the other R-101 runs. The heavy load appears to have begun during the preceding R-50 run, which has the
  largest R-50 tail (DUT-service p99 126.51 ms); host load is logged only between runs, so no cause is stated.
- The baseline DUT-service is shorter than during the golden captures (R-101 p50 179.59 ms in the capture); the
  captures ran back to back and showed lower SM clocks. The ratios do not match exactly, so this is not attributed.

## 3. Limitations

- One reference GPU, FP32, batch 1, N = 1, one replay rate per family; no NPU.
- Each family was measured on one day; timings are not compared across days. Ranges are min–max of five runs.
- The host is shared; other users' load is logged only between runs, and host preemption is not observed.
- The cuDNN math type is the default, which permits TF32 on this GPU; the numerical checks show no visible
  effect, but TF32 use is not observed.
- COCO quality uses the first 1,000 val2017 images; Cityscapes quality uses all 500 val images.
- Probe and capture runs ran in asap mode; only the fixed-rate baselines are used for timing.
- The runs were not repeated with the release code. For DeepLab the release differs only in the Python package's
  version string and a command-line help text (the native source tree is the same); for YOLOX it also adds the
  later DeepLab code and start-up checks. `code_identity` in each bundle names the code that produced it, and the
  bundles carry the package version label 0.1.0 of their time.
